GLAMLI prototypes

GLAMLI — Guided LLM-Augmented Machine Learning Interface.

COMPX520 dissertation — design prototypes exploring conversational, example-driven, and live machine-learning interfaces.

  • GLAMLI / v1 glamli_v1/

    The original staged build: a five-step workflow (Data → Columns → Examples → Spec → Train) with a left-hand rail and an LLM chat sidebar that explains each stage in plain language.

    Scenario
    An analyst working on telco churn walks through the prototype stage by stage. They upload customer_churn.csv, read the LLM's plain-language assumptions about each column and edit any that look wrong, write a few test cases of customers they expect the model to get right, and review a drafted ML spec — target column, evaluation metric (F1 on the churned class, with a one-line justification), and feature treatments. They can ask the chat sidebar "why F1-score?" at any point. When the spec looks right, they hit Confirm & Run and watch the model train.
    Idea
    Make the canonical AutoML workflow visible and explicable, but keep the user in the loop at every step. The rail enforces a deliberate sequence; the chat panel narrates and answers questions; the spec page makes the system's choices (especially the metric) editable rather than hidden. This is the baseline GLAMLI pattern — the reference point the other three prototypes (dialog, live, examples) react against, each removing or replacing one of its assumptions.
    → open prototype
  • GLAMLI / dialog glamli_dialog/

    A conversational interface that enables model building through natural language, providing iterative feedback, queries, and results without structured workflows.

    Scenario
    Maya is a domain analyst at a telco. She opens the tool with a spreadsheet on her desktop and an intent: "figure out who's about to leave us." That's the level of specificity she has. She's fluent in the language of customers and contracts and uncomfortable with the language of features, encoders, and metrics. She has no predefined goal, no evaluation metric in mind, and no patience for empty configuration screens that ask her to decide things before she's seen anything.

    The first surface she sees should ask her nothing structured, only invite her to talk.
    The idea
    The dialog is the workflow. There is no stage rail, no spec form, no "configure your task" gate. Everything the system needs — the goal, the data, a handful of example customers, the domain assumptions — is elicited through conversation. The right pane doesn't collect input; it mirrors what the system has understood so far. Four knowledge cards (Data, Domain, Examples, Goal) start as hatched empty placeholders and fill in, one at a time, as Maya talks with the system. She can shift topics, double back, or skip ahead. When the system's confidence is high enough to be useful, a single sage-tinted card at the bottom of the right pane invites her to run it — labelled, deliberately, "let's go."

    The hypothesis under test combines three findings from the CoAutoML study:
    • novices rarely arrive with a predefined ML goal
    • they struggle to identify evaluation metrics on their own
    • they learn what features matter only by watching their effect.
    A structured spec form asks them to commit to all three before they have the footing to do so. Removing the form forces elicitation into a back-and-forth where the system can scaffold one question at a time, in user-language, and where the user is never blocked on a decision they're not yet equipped to make.
    → open prototype
  • GLAMLI / live glamli_live/

    A two-pane workspace where the model is always running. Every edit produces a visible delta on the live model — pass-rate, sparkline, and test cells update as the user works. Refuses the configuration-first metaphor.

    Scenario (classification)
    Maya is a domain analyst at a telco. She opens the tool with a spreadsheet on her desktop and an intent: "figure out who's about to leave us." She's fluent in the language of customers and contracts and uncomfortable with the language of features, encoders, and metrics. She has no predefined goal, no evaluation metric in mind, and no patience for empty configuration screens that ask her to decide things before she's seen anything.

    She drops her CSV in. Within seconds, before she's done anything else, the system has trained a model on naive defaults and is showing her: "using everything in your data, my best guess on these 5 example customers is 3 right, 2 wrong." From this moment on, every change she makes produces a visible delta on the live model. She is never configuring; she is always steering.
    The idea
    The model is always running. There are no stages, no spec form, no "configure now, run later" gate — a sensible baseline trains the moment data exists, and every subsequent action retrains it. The workspace is a two-pane shell: a knowledge inbox on the left where the system surfaces suggestions as actionable cards ("split tenure into first 12 months vs after", "is contract categorical or ordinal?"), and a live panel on the right showing the current model, the five test cases passing or failing, and what's driving its predictions. Accept a card and the live pulse flips to retraining; three seconds later a test cell flips from rust to sage, the pass-rate ticks up, and the timeline gains a new entry. The user sees their decision produce a measurable improvement in real time.

    The hypothesis under test combines two CoAutoML findings. First: novices recognise the value of features only by observing their impact — so the prototype makes that impact the central, continuous artifact, not a downstream report. Second, and more pointed: when a model is underperforming, novices' overwhelming instinct is to add more data; none in the study attempted feature engineering. Live counters this directly. When Maya types "can I add more data?" into the free-chat input, the system surfaces an amber-tagged card that gently disagrees: "honestly, probably not much — the bottleneck is which columns we feed it, not how many rows." The prototype's thesis is that you teach the mental model not by explaining feature engineering but by letting the user feel a single accepted suggestion move the pass-rate from 3/5 to 4/5.
    Scenario (regression)
    Dana runs operations at a regional HVAC contractor. She has a spreadsheet of past service tickets — furnace repairs, AC maintenance, same-day diagnostics, full system installs — and a fuzzy intent: "figure out what each new job is going to be worth before we send a tech out." Some tickets are $200 tune-ups; others are $8,000 commercial installs. She wants to estimate the dollar value of incoming jobs as they land in her inbox, without learning the word regression or thinking about evaluation metrics.

    She drops her ticket history in. Within seconds, before she's done anything else, the system has trained a baseline on the 14 columns it found and is showing her: "predicting ticket_value from 14 other columns — on these 5 example tickets, I'm landing within ±20% on 3 of them. The two I'm missing on are big jobs I'm under-pricing badly." From this moment on, every change she makes produces a visible delta on the live model.
    The idea (regression)
    Structurally identical to Live's churn version: a baseline that trains on upload, an inbox of suggestions on the left, a live panel on the right, no stages, no configuration. The thesis is the same — you teach the mental model by letting the user feel a single accepted change move the dial. What changes is the readout, and the readout is most of what Dana looks at.

    Pass/fail becomes within-tolerance. Each test cell shows the predicted dollar value next to the expected one and marks ✓ if the prediction lands inside a ±20% band, × otherwise. Failing cells display the gap explicitly — predicted $3,100 / expected $8,400, 63% under — so Dana sees not just that it missed but by how much and in which direction. Direction matters here: a model that systematically under-prices urgent commercial installs is a different problem from one that's noisy in both directions, and the cells make that legible at a glance. The hero readout keeps the same Source Serif 4 typography (3/5 within ±20%), but the sparkline beneath it inverts: it tracks the model's average miss as a percentage, trending down as Dana accepts suggestions. Lower is better; the line descending is the visual analogue of cells flipping from rust to sage. The "what's driving predictions" panel surfaces the columns actually carrying the signal — equipment_type and service_type strong, urgency and equipment_age medium, building_type weak — so the next intervention is obvious: the model is doing well on routine residential work and badly on the kind of job where commercial-vs-residential and urgency interact. The signature interaction is otherwise unchanged: suggestion accepted → retrain → one more ticket in the band → average miss drops a few points. The add-more-data counter lands the same way too — when Dana asks if more rows would help, the system gently disagrees and proposes a feature-engineering move instead, almost certainly something that captures the commercial-install-under-pricing pattern the failing tests are surfacing.
    → classification (customer churn) → regression (service-ticket value)
  • GLAMLI / examples glamli_examples/

    An example-driven flow where the user drops a CSV and teaches the model by labelling three to five rows. The system predicts the rest and surfaces the cases that didn't match cleanly.

    Scenario
    Same churn dataset (7,043 rows · 21 columns). Instead of picking a target column, the user describes a few real customers in plain prose — "a customer on a month-to-month plan paying about $90/month" — and labels each as will churn or will stay. The system maps the descriptions to columns, trains, and reports which of the user's own examples it got right.
    Idea
    Teach by example, not by schema. The user never has to know the column names; the LLM grounds their language in the data and uses the examples both as training signal and as the test the model must pass.
    → open prototype
